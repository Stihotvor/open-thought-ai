# T3: PendingCalls, tool.result routing and DeviceSession.close

## Context
The server sends `tool.call` and must match the device's `tool.result` to the waiting call (T2, decision D6). This task builds `PendingCalls`, routes `tool.result` in every session state, and closes all waits when the socket closes. It serves E3, E4, E6, F3, M5. T4 uses `PendingCalls` and T6 builds the device source from `DeviceSession.pending`.

## Technical Approach
New `server/src/ota_server/hub/pending.py`. It must not import `session.py`. Public names (T4 uses them):
```python
@dataclass(frozen=True)
class DeviceResult:
    ok: bool
    text: str          # result as text, or the error text

class PendingClosed(Exception):   # set on a waiting future by fail_all

class PendingCalls:
    def new_id(self) -> int       # session-unique counter, starts at 1, never reused
    async def wait_for(self, call_id: int, timeout: float,
                       send: Callable[[], Awaitable[None]]) -> DeviceResult
    def resolve(self, msg: dict[str, Any]) -> bool    # True when a waiting call got the result
    def fail_all(self) -> None    # every waiting future gets PendingClosed
    def __len__(self) -> int      # number of waiting ids
```
- `wait_for` registers the future for `call_id`, awaits `send()`, then waits for the future up to `timeout` seconds. It raises `TimeoutError` on expiry and `PendingClosed` after `fail_all`. A `finally` block always removes the id (D6), also on cancel or on an error from `send`.
- `resolve(msg)`: `msg["id"]` must be an `int` (not `bool`) and known, else log at info level, ignore, return False (E3). A known id with a bad shape gets `DeviceResult(False, "malformed tool.result")` (E4). Bad shape means: `ok` is not a `bool`, or `ok` is False and `error` is not a `str`. `ok` True gives the text of `result` (a `str` as is, other JSON by `json.dumps`, missing as `"ok"`). `ok` False gives the `error` text. An id that was answered is removed, so a second result is unknown.
- `server/src/ota_server/session.py`: `DeviceSession.__init__` creates `self.pending = PendingCalls()`. In `handle_text` add `case "tool.result": self.pending.resolve(msg)`. It runs in every state (listening, thinking, speaking). Add `async def close(self) -> None`: call `self.pending.fail_all()`, then `await self.cancel_reply()`.
- `server/src/ota_server/gateway.py`: in the final `finally`, keep `slot.release(ws)` first, then `await session.close()` instead of `await session.cancel_reply()`.
- Do not change `protocol.py`: a `tool.result` with a bad shape is a handled result, not a `ProtocolError`.

## Acceptance Criteria
```gherkin
Scenario: Result resolves the wait in every state
  Given a call waits with id 1 while the session is idle, listening or speaking
  When handle_text gets {"type":"tool.result","id":1,"ok":true,"result":"30"}
  Then the wait returns DeviceResult(True, "30")
  And len(pending) is 0

Scenario: Unknown or answered id
  Given no call waits with id 99, and id 1 was already answered
  When handle_text gets a tool.result for id 99 and then again for id 1
  Then both calls are ignored and logged
  And the session does not raise
  And the next listen.start and reply work

Scenario: Malformed result for a known id
  Given a call waits with id 2
  When handle_text gets {"type":"tool.result","id":2,"ok":"yes"}
  Then the wait returns DeviceResult(False, "malformed tool.result")

Scenario: Malformed result for an unknown id
  Given no call waits with id 7
  When handle_text gets {"type":"tool.result","id":7}
  Then it is ignored and the session survives

Scenario: Error result
  Given a call waits with id 3
  When the device sends ok false and error "busy"
  Then the wait returns DeviceResult(False, "busy")

Scenario: Ids are session-unique
  Given two turns in one session
  When new_id is called in each turn
  Then no id repeats

Scenario: Abort leaves no entry
  Given a reply task waits in wait_for
  When the session gets abort for the turn
  Then the wait is cancelled
  And len(pending) is 0

Scenario: Timeout leaves no entry
  Given wait_for with timeout 0.05 and no result
  When the time passes
  Then it raises TimeoutError and len(pending) is 0

Scenario: Close fails all waits
  Given 2 calls wait
  When the gateway closes the socket and calls session.close()
  Then both waits raise PendingClosed
  And no extra asyncio task is left running
```
