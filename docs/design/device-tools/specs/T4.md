# T4: Device source and McpHub

## Context
The LLM must reach the three fixed device tools through the hub (T3 and T4 constraints, decisions D2, D4, D12). This task builds the device tool source with the 2 s timeout and the `McpHub` that lists tools and runs calls through the chain from T1. It serves B1, B2, E1, E2, E5, F1, F2, M1, M2, M3, M4 and M6.

## Technical Approach
Use the types from T1 (`hub/types.py`) and `PendingCalls`, `DeviceResult`, `PendingClosed` from T3 (`hub/pending.py`). Do not import `session.py`.

`server/src/ota_server/hub/device_source.py`:
```python
DEVICE_TIMEOUT = 2.0
FACES = ("idle", "listening", "thinking", "speaking", "offline", "error")   # firmware/main/face.h

class DeviceSource:                 # implements ToolSource
    name = "device"
    def __init__(self, send: Callable[[dict[str, Any]], Awaitable[None]],
                 pending: PendingCalls, timeout: float = DEVICE_TIMEOUT) -> None: ...
    def specs(self) -> list[ToolSpec]: ...
    async def call(self, tool: str, args: dict[str, Any]) -> ToolOutcome: ...
```
- `specs()` returns three `ToolSpec` with `confirm=False`: `set_volume` (object, required `level`, integer 0..100, `additionalProperties: false`), `set_face` (required `face`, string, enum `FACES`), `get_status` (empty object, `additionalProperties: false`).
- `call()`: `call_id = pending.new_id()`, frame `{"type": "tool.call", "id": call_id, "name": tool, "args": args}`. Compute the size as `len(json.dumps(frame, separators=(",", ":")).encode())`. Over `MAX_TEXT_FRAME` (1024, from `protocol.py`): return `ToolOutcome(False, "tool call too large", "frame_too_large")` and send nothing. Else `await pending.wait_for(call_id, self.timeout, lambda: send(frame))`.
- Outcomes: `DeviceResult(True, t)` gives `ToolOutcome(True, t)`. `DeviceResult(False, t)` gives `ToolOutcome(False, t, "device_error")` (F2). `TimeoutError` gives `ToolOutcome(False, "tool_timeout", "tool_timeout")` and a warning log (F1). `PendingClosed` gives `ToolOutcome(False, "device disconnected", "device_closed")`. Any other `Exception` from `send` gives `ToolOutcome(False, "could not send tool call", "send_failed")`. `CancelledError` is not caught.

`server/src/ota_server/hub/hub.py`:
```python
class McpHub:
    def __init__(self, sources: Sequence[ToolSource]) -> None: ...
    def list_tools(self) -> list[dict[str, Any]]
    async def run(self, call: ToolCall, ctx: CallCtx) -> ToolOutcome     # never raises
    def turn_context(self) -> ToolContext                                # new CallCtx, bound to this hub
```
- `list_tools()` returns `{"type": "function", "function": {"name": spec.full_name, "description": ..., "parameters": spec.schema}}` for each spec, so `device__set_volume`, `device__set_face`, `device__get_status`.
- The constructor builds the spec map by full name and the chain: `build_chain([resolve(specs), limit(), validate(specs), wrap()], terminal)`. The terminal finds the source by the part before `SEP` and calls `source.call(bare_tool, call.args)`.
- `run()` calls the chain. Any `Exception` becomes `ToolOutcome(False, "tool failed", "internal")` and is logged. `CancelledError` goes through.
- `turn_context()` returns an object (class `TurnTools`, in `hub.py`) with `list_tools()` and `run(call)` that calls `hub.run(call, ctx)` with one `CallCtx` for the whole turn.

## Acceptance Criteria
```gherkin
Scenario: Tool list
  Given an McpHub with a DeviceSource
  When list_tools is called
  Then it returns 3 entries named device__set_volume, device__set_face, device__get_status
  And device__set_face has an enum of the 6 faces

Scenario: Volume call
  Given a fake send and a fake PendingCalls that answers ok
  When run gets device__set_volume {"level": 30}
  Then send got exactly 1 frame {"type":"tool.call","id":<int>,"name":"set_volume","args":{"level":30}}
  And the outcome has ok True

Scenario: Timeout
  Given a real PendingCalls and a fake send that never answers
  When run gets a valid device__get_status call
  Then the outcome has ok False and code "tool_timeout"
  And it came after 2.0 s plus or minus 0.2 s

Scenario: Device error
  Given the device answers ok false with error "no speaker"
  When run gets a valid call
  Then the outcome has ok False, code "device_error" and a text that contains "no speaker"

Scenario: Six calls in one turn
  Given one turn context
  When run gets 6 valid get_status calls
  Then send got exactly 4 frames
  And calls 5 and 6 have code "call_limit"

Scenario: Unknown tool and invalid args send nothing
  Given a fake send
  When run gets device__nope, set_volume level 150, set_volume without level, and set_volume level "x"
  Then every outcome has ok False
  And send got 0 frames

Scenario: Oversized frame
  Given a source with a tool name or args that make the frame over 1024 bytes
  When call runs
  Then the outcome has code "frame_too_large"
  And send got 0 frames

Scenario: Frames fit
  Given the valid calls of all 3 tools
  When their frames are serialized
  Then each is at most 1024 bytes

Scenario: Device closed or send fails
  Given PendingCalls that raises PendingClosed, or a send that raises OSError
  When run gets a valid call
  Then the outcome has code "device_closed" or "send_failed"
  And run did not raise
```
