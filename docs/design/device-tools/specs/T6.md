# T6: Session builds McpHub per turn and end-to-end test

## Context
The parts from T3, T4 and T5 must work together in a real session turn (decision D7). The session builds one `McpHub` with a `DeviceSource` for each turn and passes it to the reply source. This task serves B1, B3, E6, E8, M1, M2, M7. It has no new design: it wires and tests.

## Technical Approach
`server/src/ota_server/session.py`:
- In `produce()` always call `self.reply_source(pcm, history, notify=notify, tools=self.turn_tools())`. Echo ignores `tools` (its signature was changed in T5). Every reply source fake in tests must accept the `tools` keyword.
- New method `turn_tools(self) -> ToolContext`: `McpHub([DeviceSource(self.ws.send_json, self.pending)]).turn_context()`. The hub and its `CallCtx` live for one turn, so the 4-call cap is per turn (D5). `self.pending` comes from T3.
- Abort uses the existing `cancel_reply`: it cancels the reply task, the wait ends and its `finally` removes the id (T3). Ids are session-unique, so a late result of the aborted call does not match a call of the next turn.
- Existing test fakes of a reply source that lack the `tools` keyword must get it. This is a test-only edit.

`server/tests/test_device_tools_e2e.py`: a real `VoicePipeline` with a `ModelClient` on an `httpx.MockTransport` (fake STT, moderation, chat and TTS endpoints), and a fake socket that records `send_json` and lets the test call `session.handle_text`. No real API call and no board.
- The fake chat answers the first request with a `tool_calls` stream for `device__set_volume {"level": 30}` and the second request (which has a `tool` message) with text.
- Run `pytest --cov=ota_server` for the whole suite. Coverage for the new `hub/` code and the new lines must be at least 90 %.

## Acceptance Criteria
```gherkin
Scenario: Volume turn end to end
  Given a session with VoicePipeline, a fake chat that calls device__set_volume {"level": 30}, and a fake socket
  When the user turn runs and the fake device answers tool.result ok for the sent id
  Then the socket got exactly 1 frame {"type":"tool.call","name":"set_volume","args":{"level":30}} with an int id
  And the socket got reply audio for the final text
  And the socket got reply.end with reason "done"

Scenario: No tool.result
  Given the same session and a device that never answers
  When the turn runs
  Then the tool outcome has code "tool_timeout" after 2.0 s plus or minus 0.2 s
  And the LLM got the timeout text in the tool message
  And the turn still ends with reply.end

Scenario: Abort during the wait
  Given a tool.call is sent and the device has not answered
  When the session gets abort for the turn
  Then the wait is cancelled and the pending list is empty
  And the socket got reply.end with reason "abort"

Scenario: Late result after abort
  Given the aborted call had id N
  When the device sends tool.result for id N during the next turn
  Then the result is ignored
  And the next turn finishes with its own call and result unchanged

Scenario: Echo unchanged
  Given a session with the echo reply source
  When a turn runs
  Then echo gets a tools argument and ignores it
  And the reply is the same as before
  And all existing session and gateway tests pass

Scenario: Cap per turn
  Given a fake chat that asks for 6 tool calls in one turn
  When the turn runs
  Then the socket got exactly 4 tool.call frames

Scenario: Full suite
  Given the whole server test suite
  When pytest runs with coverage
  Then all tests pass
  And ruff and mypy report 0 errors
  And coverage of the new code is at least 90 percent
```

## Definition of Done
- The task's `done_when` check passes.
- Tests exist for every scenario and pass.
- The quality gate reports pass or skipped (never fail).
- No `OPEN:` item remains.
