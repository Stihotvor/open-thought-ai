# T5: confirm chain step after validate

## Context
The hub must hold a risky call before any source runs it, so the LLM and the pipeline cannot skip it (requirements B1, T2, T3, E1, E8, E9, F3, F4). The step is the enforcement point. It serves M1.

## Technical Approach
Per D3.
- `hub/steps.py`: add `confirm(specs: Mapping[str, ToolSpec], gate: ConfirmGate) -> Step`, same factory style as `validate`.
  - Spec for `call.name` has `confirm=False`: `return await next_(call, ctx)` (E8).
  - Otherwise build `Held(call.name, dict(call.args), call.id, ctx.turn)` (args are validated, so a dict). If `gate.hold(held)` is True return `ToolOutcome(False, "held: the user must say yes", "confirm_required")`. If False return `ToolOutcome(False, "another call already waits for a yes", "confirm_busy")`.
  - Wrap the body in `try/except Exception`: `log.error(..., exc_info=True)` and return `confirm_required`. Nothing runs (F4). Add `import logging` to `steps.py`.
- `hub/hub.py`: `McpHub.__init__` creates `self._gate = ConfirmGate()` and a public read-only property `gate` (the session arms it in T8). The chain becomes `[wrap(), resolve(self._specs), limit(), validate(self._specs), confirm(self._specs, self._gate)]`.
- `limit()` runs before `confirm`, so a held call counts toward the cap of 4 (E9). No change to `limit`.
- Tests in `server/tests/test_confirm_step.py` with a fake `ToolSource` (a device-like and an MCP-like one) that counts calls.

## Acceptance Criteria
```gherkin
Scenario: A confirm=false call passes
  Given a spec with confirm False and a fake source
  When the call runs through the hub
  Then the source gets 1 call and the gate is empty

Scenario: A confirm=true call is held
  Given a spec with confirm True, for a device-like and an MCP-like fake source
  When the call runs
  Then the outcome is ok False with code "confirm_required" and text containing "held: the user must say yes"
  And the source gets 0 calls
  And the gate holds that call

Scenario: A second confirm call is busy
  Given a held call in the gate
  When a second confirm=true call runs in the same turn
  Then the outcome code is "confirm_busy" and the source gets 0 calls

Scenario: A normal call beside a held call runs
  Given a held call and a confirm=false call in the same turn
  When the second call runs
  Then the source gets 1 call

Scenario: A step bug fails closed
  Given a gate whose hold raises an exception
  When a confirm=true call runs
  Then an error is logged, the outcome code is "confirm_required" and the source gets 0 calls

Scenario: Chain order
  Given the hub chain
  When the step order is read
  Then it is wrap, resolve, limit, validate, confirm, terminal

Scenario: The held call counts toward the cap
  Given a CallCtx with 3 calls done
  When one confirm=true call is held, then a 5th call runs
  Then the 5th gets code "call_limit"
```

## Definition of Done
- The task's `done_when` check passes.
- Tests exist for every scenario and pass.
- The quality gate reports pass or skipped (never fail).
- No `OPEN:` item remains.
