# T3: 0001_initial migration and Postgres integration tests

## Context
The first migration creates the full schema from `docs/data-model.md` and seeds two rows. It serves constraint 6 and the success metrics (up/down/up, parallel runners, failed migration leaves nothing). #33 to #37 build on this schema.

## Technical Approach
- `server/src/ota_server/db/migrations/versions/0001_initial.py` (decision rule 10):
  - Tables: `conversation`, `turn`, `settings`, `mcp_server`, `tool`. Use the columns, checks, foreign keys (ON DELETE CASCADE where listed) and indexes in `docs/data-model.md`, "Constraints (first migration)".
  - Name every constraint. No `pgcrypto`. Use core `gen_random_uuid()`. No `CONCURRENTLY`. One transaction.
  - `settings` defaults NOT NULL: `language 'en'`, `voice ''`, `system_prompt ''`, `volume 50`. Seed with `INSERT ... DEFAULT VALUES ON CONFLICT DO NOTHING`.
  - Seed `mcp_server` row `name='device'`, `transport='device'`, `url NULL`, with `ON CONFLICT DO NOTHING`.
  - `downgrade()` drops all five tables.
  - No schema name in the file.
- `server/tests/integration/conftest.py`: read `OTA_TEST_DATABASE_URL`. Skip all tests in the folder when it is not set. Use a unique `DEVICE_ID` per test and drop the schema after.
- `server/tests/integration/test_migrations_pg.py`: tests below, calling `migrate()` from T2.

## Acceptance Criteria
```gherkin
Scenario: Upgrade, downgrade, upgrade
  Given an empty Postgres 16 database and a DEVICE_ID
  When migrate runs upgrade head, then downgrade -1 with the allow flag, then upgrade head
  Then each step exits without error
  And after the last step the five tables exist in schema ota_<device_id>
  And after the downgrade step none of the five tables exist

Scenario: Second run changes nothing
  Given a database already at head
  When migrate runs again
  Then it exits without error
  And alembic_version still has one row with the same revision

Scenario: Seeds
  Given a database at head
  When the settings and mcp_server tables are read
  Then settings has one row with language 'en', voice '', system_prompt '' and volume 50
  And mcp_server has exactly one row, named 'device' with transport 'device'

Scenario: Failed migration leaves nothing
  Given a test revision that creates a table, then fails
  When migrate runs
  Then it raises an error
  And no table from that revision exists
  And the advisory lock is free (pg_try_advisory_lock succeeds from another session)

Scenario: Two parallel runners
  Given an empty database and two migrate processes started together
  When both finish
  Then both exit 0
  And the version table has one row

Scenario: A long wait is not cancelled
  Given a runner holds the lock for more than 10 s
  And a second runner uses a role with statement_timeout 10 s
  When the first runner releases the lock
  Then the second runner exits 0 without a timeout error

Scenario: Constraints hold
  Given a database at head
  When a second 'device' mcp_server row is inserted
  Then the insert fails with a unique violation
  And inserting a turn with role 'x' fails with a check violation

Scenario: No test database
  Given OTA_TEST_DATABASE_URL is not set
  When pytest runs tests/integration
  Then every test is reported as skipped and pytest exits 0
```

## Definition of Done
- `cd server && OTA_TEST_DATABASE_URL=<postgres 16 url> pytest tests/integration/test_migrations_pg.py` passes.
- Without the variable, the tests skip and pytest exits 0.
- Tests exist for every scenario and pass.
- ruff and mypy report 0 errors. The quality gate reports pass or skipped (never fail).
- No `OPEN:` item remains.
