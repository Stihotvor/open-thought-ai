# T4: SdkConnection reconnect: lock, generation counter and one retry

## Context
A shared connection can drop between turns (F2) or a stdio child can exit (F3). The connection must reconnect once per call without a double reconnect and without a half-done state. This task serves T6, E7, F2, F3, M2, M3, D6 and D7. It changes `adapters.py` from T3 and relies on the `McpSource` timeout from T2.

## Technical Approach
Edit `server/src/ota_server/mcp/adapters.py`. The `McpSource` (T2) stays unchanged: its `asyncio.timeout` wraps the whole `call_tool`, including reconnect and retry (D6).

In `SdkConnection`:
- Module constant `RECONNECT_TIMEOUT = 5.0`, read at call time so tests patch it small.
- Keep an `asyncio.Lock` and an `int` generation counter. A reconnect stops the old owner task (same stop path as `close`, with `STOP_TIMEOUT` from T3), then starts a new owner task through the same `open` path, including `policy.before_connect` (D11: before each connect and reconnect). Generation goes up by 1 after a successful reconnect.
- One `asyncio.timeout(RECONNECT_TIMEOUT)` covers both steps: the stop of the old owner and the open of the new one (D7). The stop inside it must also end by that deadline: when the deadline passes, cancel the old owner task. A hung server cannot hold the lock longer than `RECONNECT_TIMEOUT`.
- `call_tool`: read the generation, call the shared session. Only a transport error starts a reconnect (D7): closed stream (`anyio.ClosedResourceError`, `anyio.BrokenResourceError`, `anyio.EndOfStream`), `httpx.TransportError`, `McpError` that signals a closed connection, or a dead owner task (child exit). An `McpError` for a tool-level fault and a timeout do not reconnect.
- `reconnect(seen_generation)`: run under the lock and wrapped in `asyncio.shield`, so a caller cancel or timeout cannot leave it half done. Under the lock, if the current generation is newer than `seen_generation`, return without reconnect (two concurrent failed calls cause one reconnect). On failure, raise, and the caller gets the error. The connection stays in a state where the next call tries a reconnect again.
- After a successful reconnect, retry the call once. A second failure raises, and `McpSource.call` turns it into an error outcome (F2, F3).
- Tool list is not refreshed on reconnect (known limit in `decision.md`).

Tests in `server/tests/test_mcp_reconnect.py` use the fakes from T3 (`mcp_fakes.py`, `mcp_stdio_server.py`). Count reconnects with a recording `ConnectionPolicy` (`before_connect` calls beyond the first) or with the generation counter. Patch `RECONNECT_TIMEOUT` small in the hung-server test and assert the call ends within the patched value plus 0.5 s. A second test asserts the constant default is 5.0.

## Acceptance Criteria
```gherkin
Scenario: Http server restarts
  Given an open http connection and a fake server that restarts on the same port
  When call_tool runs after the restart
  Then 1 reconnect happened
  And the call returns the correct result

Scenario: Stdio child exits
  Given an open stdio connection and the child PID from the "pid" tool, killed with SIGKILL
  When call_tool runs
  Then 1 restart happened
  And the call returns the correct result
  And the new child has a different PID

Scenario: Concurrent failed calls reconnect once
  Given an open http connection and a restarted server
  When two call_tool calls run at the same time
  Then the generation went up by 1
  And both calls return a result

Scenario: Reconnect fails, then the server returns
  Given an open http connection through an McpSource and the fake server is stopped
  When call runs
  Then the outcome has ok False
  And the session task is still alive
  When the fake server restarts on the same port and call runs again
  Then the outcome has ok True through a new reconnect

Scenario: Hung server during reconnect
  Given RECONNECT_TIMEOUT patched to 0.5 and a server that accepts the socket and never answers initialize
  When call_tool triggers a reconnect
  Then the call ends within 0.5 s plus 0.5 s
  And the lock is free for the next call

Scenario: Hung old owner during reconnect
  Given an old owner whose exit blocks until cancelled and RECONNECT_TIMEOUT patched to 0.5
  When a reconnect runs
  Then the stop of the old owner and the open of the new one end together within 0.5 s plus 0.5 s

Scenario: Concurrent calls on one connection
  Given one open http connection and a tool that waits 0.2 s and returns its input
  When two calls with different inputs run at the same time
  Then each call gets the result of its own input
  And 0 reconnects happened

Scenario: Call after a timeout
  Given an McpSource over a real http connection with timeout 1 and a tool that sleeps 3 s once
  When the first call runs
  Then it returns ok False with code "tool_timeout" within 1.5 s
  When a second fast call runs
  Then the second call succeeds
  And 0 reconnects happened

Scenario: Policy runs on reconnect
  Given a recording ConnectionPolicy
  When a reconnect happens
  Then before_connect ran once more before the new transport opened

Scenario: Defaults
  Given the module adapters
  When the test reads the constants
  Then RECONNECT_TIMEOUT is 5.0
```
